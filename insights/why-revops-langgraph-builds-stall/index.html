Why RevOps LangGraph builds stall after the demo

The graph works on Friday. Production is a different system.

Michael Bogart · CEO & Chief Revenue Architect, Revenue-Growth.AI · August 24, 2026

The graph works on Friday. By Wednesday the Salesforce Task object has twins, the forecast field is an argument, and the engineer you borrowed is back on the product roadmap.

That is the stall. It is not “AI is hard.” It is a specific production gap between a LangGraph notebook and a RevOps system that is allowed to write.

The demo is one opportunity

Composite, labeled as such: a Series B RevOps lead, Salesforce, ~$18M ARR, one friendly backend engineer. They wire four nodes.

Pull the Opportunity. Score it. Draft a next step. Write the Task.

They put interrupt() in front of the write. They click through one sandbox record. The AE would have written the same next step. Leadership sees a recording. The project is “basically done.”

It is not. They have proven that Claude can read a record. They have not proven that a graph can inspect the book of business tonight, pause for a human, survive a deploy, and write once.

Resume restarts the node

This is the mechanism that wrecks the first production week.

LangGraph’s interrupt() pauses a node and checkpoints state. When you resume with Command(resume=...), the interrupted node does not continue from the line after interrupt(). It starts at the top of that node.

Anything before the pause runs again. If that anything was sf.Task.create(...), Salesforce now has two Tasks. Two next steps. A Stage or NextStep field that flipped twice. The activity timeline looks like a drunk intern.

The fix is a dedicated approval node that does nothing except interrupt(), plus idempotent writes keyed on something you already own (Opportunity Id + date + agent version). Teams learn this after the duplicates, not before.

Until then, the AE does not debate the model. They debate the CRM.

Memory that forgets on deploy

The second silent killer is the checkpointer.

InMemorySaver is what the tutorial uses. It lives in RAM. Restart the process and every pending approval is gone. The graph has no memory of the twelve deals it paused for a manager who had not yet clicked.

Production needs PostgresSaver or equivalent, a stable thread_id per deal, and a policy for checkpoint growth. LangGraph will not prune that store for you. Interrupted threads also sit forever. There is no native “if nobody approves in 30 minutes, escalate or fail closed.”

So the first ECS deploy, the first Fargate task recycle, or the first “we had to bounce it” becomes a pile of orphaned deals. RevOps thinks the agent stalled. The agent thinks it is still waiting on a thread that no longer exists.

MCP is a wire

Connecting a model to Salesforce or HubSpot through MCP (or a thin REST wrapper) is real work. It is also the first 10% of the build.

A wire lets the model query. A worker has to do the rest: a nightly pass, webhook ingress, scoped credentials, retries, dead letters, eval, and an audit trail of every write. Persona prompts (“act like a RevOps analyst”) do not encode your MEDDPICC, your stage-exit rules, or the way you actually call a slip.

Zapier or Make bolted on as “tools” fails here for a different reason. Those runners are if/then. They have no durable graph state, no interrupt that survives a crash, and a bill that scales with task volume exactly when pipeline volume is the point.

Shared SaaS AI fails the other way. The SOC 2 review starts. Customer data leaves the VPC. Security is now on the critical path. The graph did not stall. The ticket did.

Approval is not a Slack message

interrupt() was built for an interactive session. You, the terminal, a click.

A RevOps write is not that session. The approver is a manager in Slack who might answer in two hours. LangGraph does not email them. It does not post to a channel. It does not log who approved, when, or why. Graph state is not an audit log.

You will build notifications, a timeout, escalation, and a human-readable record of every CRM write. That is not extra polish. That is the job, because an unsupervised write to Amount, CloseDate, or NextStep is how you lose the floor.

Salesforce will throttle the nightly pass

Even a correct graph still has to live inside CRM physics.

Salesforce production orgs cap concurrent inbound API calls that run 20 seconds or longer at 25. New long-running calls then get REQUEST_LIMIT_EXCEEDED until the queue drains. A naive loop (SOQL + long context + a model call, per open Opportunity) will sit in that bucket. LeanData, Gong, Outreach, and your own integrations still need the same daily allocation.

HubSpot is kinder on paper and still punishes chatty writeback, duplicate associations, and missing idempotency.

The “inspect every deal, every night” idea dies here if you treat the CRM as an unbounded database. It is not. It is a shared production API with a number on it.

One bad write and the forecast is politics

This is why deals stall.

The first duplicate Task is funny. The third is a Slack thread. By the time a CloseDate moves with no AE fingerprint, inspection time goes up, not down. The board number is “the AI number.” Reps sandbag because they do not know which fields the graph will touch overnight.

You did not buy speed. You bought a second source of truth, then spent the quarter reconciling it.

The build-versus-buy tension is real, and it is not Zapier. The real alternative to this path is still a LangGraph graph. The question is whether you want to own the replay bugs, the checkpointer, the HITL plumbing, and the Salesforce backoff yourself, in an AWS account you control, or whether that graph should already be running as infrastructure in your VPC.

Control was the right instinct. Data should not leave. A notebook is not control. Control is idempotent writes, scoped IAM, logs in your CloudWatch, and a graph that can be torn down on purpose.

If your graph cannot inspect tonight’s book without writing a duplicate Task, you do not have an agent. You have a demo that got permission to touch production.
